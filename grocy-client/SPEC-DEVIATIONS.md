# Grocy OpenAPI spec deviations and manual client fixes

This module is generated by OpenAPI Generator from grocy's published spec
(`https://raw.githubusercontent.com/grocy/grocy/master/grocy.openapi.json`), but the spec,
the actual server behavior, and the generator's Kotlin output disagree in several places.
This file is the authoritative catalogue of every manual intervention: what is broken,
the evidence, the workaround applied here, how the workaround survives regeneration, and
the fix we would propose upstream.

**Goal:** this catalogue is the raw material for a future report and pull request against
[grocy/grocy](https://github.com/grocy/grocy) fixing `grocy.openapi.json`. Keep it updated:
any new manual fix to this module MUST add an entry here.

All evidence below was captured against `https://en.demo.grocy.info` (grocy demo server)
and the spec as of **2026-07-09**.

## How workarounds are protected from regeneration

`regenerate.sh` deletes and replaces `src/commonMain`, `src/test` and `docs/`, so plain
manual edits do not survive. Three mechanisms do:

1. **Hand-written files** listed in `.openapi-generator-ignore` — `regenerate.sh` copies
   them aside before replacing sources and restores them afterwards.
2. **sed post-fixes** in `regenerate.sh` — for corrections inside otherwise-generated
   files (re-applied on every regeneration).
3. **Generation-time flags** in `regenerate.sh` — `--type-mappings`, `--skip-validate-spec`.

Regression guard: `data/src/jvmTest/.../datasource/remote/generic/GenericEntityDeserializationTest.kt`
decodes real server payload shapes; if a regeneration loses a fix, that test fails.

After any regeneration run: `./gradlew :grocy-client:compileKotlinJvm :data:test`.

## 1. Server serializes DB-backed booleans as `0`/`1` integers (spec declares `boolean`)

**The core inconsistency:** grocy serializes database-backed boolean fields as `0`/`1`
integers, but PHP-computed boolean fields as real `true`/`false` — while the spec declares
both `boolean`.

Spec properties declared `type: boolean` (as of 2026-07-09):
`RecipeFulfillmentResponse.need_fulfilled`, `RecipeFulfillmentResponse.need_fulfilled_with_shopping_list`,
`ProductDetailsResponse.has_childs`, `Chore.track_date_only`, `Chore.rollover`,
`StockLogEntry.spoiled`, `StockJournal.spoiled`, `CurrentStockResponse.is_aggregated_amount`,
`CurrentChoreResponse.track_date_only`, `CurrentChoreResponse.is_rescheduled`,
`CurrentChoreResponse.is_reassigned`.

**Evidence (demo server, 2026-07-09):**
- `GET /api/stock` → `"is_aggregated_amount": 0` (integer; spec says boolean).
- `POST /api/stock/products/{id}/add` response → `"spoiled": 0` (integer; spec says boolean).
- `GET /api/stock/products/{id}` → `"has_childs": false` (real boolean — computed in PHP).

Note the DB-row schemas themselves (e.g. `Product.should_not_be_frozen`) are declared
`integer` in the spec, matching the server — the mismatch is confined to the response
schemas above.

**Workarounds here:**
- `--type-mappings boolean=kotlin.Int` in `regenerate.sh` — makes the `0`/`1` fields decode.
- sed post-fix rewriting generated defaults `kotlin.Int? = false/true` → `= 0/1`
  (the generator copies boolean literal defaults from the spec into the Int-typed fields,
  which would not compile).
- `ProductDetailsResponse.has_childs` is the counter-case broken *by* the mapping (server
  sends `true`/`false`, mapped type was `Int?`): retyped to
  `kotlinx.serialization.json.JsonElement?` via a dedicated sed post-fix. Nothing in the
  app reads it.

**Proposed upstream fix:** serialize the fields listed above as real JSON booleans (or
re-declare them `integer` like the DB-row schemas — either way, make spec and server agree).

## 2. `userfields`: server sends a JSON object; generated client expected a string

The server includes `userfields` in `/objects/{entity}` rows only when userfields are
defined for that entity, and it is always a JSON **object** (e.g.
`"userfields": {"shop_sort": null}` on `GET /api/objects/products` with a `shop_sort`
userfield configured; values can be strings: `{"shop_sort": "42"}`).

The current spec declares it `type: object` (correct, no `additionalProperties`), but the
Kotlin generator maps a property-less `object` to `kotlin.String`, producing a field that
throws on every decode as soon as an instance defines userfields for the entity. This broke
the purchase screen's product list against the demo server.

**Workaround here:** sed post-fix in `regenerate.sh` retypes
`userfields: kotlin.String?` → `kotlinx.serialization.json.JsonElement?` in **all**
generated models (`Battery`, `Chore`, `Location`, `ObjectsEntityGet200ResponseInner`,
`Product`, `QuantityUnit`, `ShoppingListItem`, `ShoppingLocation`, `Task`). `JsonElement?`
tolerates object, string and null. Nothing in the app reads the field.

**Proposed upstream fix:** declare it
`type: object, additionalProperties: true, nullable: true` so generators produce a map/dynamic
type instead of guessing. (Secondary: this is also a reportable openapi-generator Kotlin
issue — property-less `object` should not map to `String`.)

## 3. Timestamps are not RFC 3339 despite `format: date-time`

The spec declares fields like `row_created_timestamp` as `type: string, format: date-time`,
but the server sends `"2026-07-09 00:50:06"` — space separator, no timezone — which is not
RFC 3339 / ISO 8601 and fails any spec-conformant date-time parser.

**Workaround here:** `--type-mappings DateTime=kotlin.String` in `regenerate.sh` — all
date-time fields are plain strings client-side.

**Proposed upstream fix:** either emit RFC 3339 timestamps or drop `format: date-time`
(e.g. declare a `pattern`).

## 4. Dangling `$ref`s: entity-enum schemas referenced but never defined

Path parameters `$ref` five schema names that do not exist in `components/schemas`
(verified 2026-07-09):

- `ExposedEntity_IncludingUserEntities`
- `ExposedEntity_IncludingUserEntities_NotIncludingNotEditable`
- `ExposedEntity_NotIncludingNotDeletable`
- `ExposedEntity_NotIncludingNotEditable`
- `ExposedEntity_NotIncludingNotListable`

The generator emits imports for the missing models, and the partial enums it does produce
are wrong: `ExposedEntityNoEdit` lists the *non-editable* entities (so `objectsEntityPost`
could not create products), and `ExposedEntityNoListing` contains only `api_keys` (so
`objectsEntityGet` could not list anything useful).

**Workaround here:** hand-written
`src/commonMain/kotlin/org/openapitools/client/models/ExposedEntityTypeAliases.kt`
aliases all five names to the complete `ExposedEntity` enum. Protected via
`.openapi-generator-ignore`.

**Proposed upstream fix:** define those five schemas in `components/schemas` with the
correct entity subsets.

## 5. `quantity_unit_conversions` entity has no schema

The entity is exposed via `/objects/{entity}` but `from_qu_id`/`to_qu_id`/`factor` appear
nowhere in `components/schemas`, so the generic-entity model cannot carry its fields and no
typed model is generated.

**Workaround here:** hand-written
`src/commonMain/kotlin/org/openapitools/client/models/QuantityUnitConversion.kt` and
`src/commonMain/kotlin/org/openapitools/client/apis/QuantityUnitConversionsApi.kt`.
Protected via `.openapi-generator-ignore`.

**Proposed upstream fix:** add a `QuantityUnitConversion` schema and include its fields in
the generic-entity response schema.

## 7. `shopping_list` rows: server sends `done` and `qu_id`; spec omits both

The `ShoppingListItem` schema (and therefore the merged generic-entity response schema)
declares only `id`, `shopping_list_id`, `product_id`, `note`, `amount`,
`row_created_timestamp` and `userfields` — but the server includes two more columns on
every row, and `done` is the only way to persist a crossed-off state (the grocy web UI
uses it).

**Evidence (demo server, 2026-07-09):**
- `GET /api/objects/shopping_list` → rows include `"done": 0` and `"qu_id": 3`
  (after `POST /api/stock/shoppinglist/add-missing-products`).
- `PUT /api/objects/shopping_list/{id}` with body `{"done":1}` → 204, and the row
  reads back `"done": 1` — the round-trip the shopping list screen relies on.

`done` is serialized as a `0`/`1` integer (DB-backed boolean, consistent with item 1).

**Workarounds here:** sed post-fixes in `regenerate.sh` add
`done: kotlin.Int?` to `ObjectsEntityGet200ResponseInner` and `ShoppingListItem`, and
`quId: kotlin.Int?` to `ShoppingListItem` (`ObjectsEntityGet200ResponseInner` already has
`qu_id` via the recipe-position schema). Reads and the partial-body `PUT` both go through
`ObjectsEntityGet200ResponseInner`; the client's `Json` leaves `encodeDefaults` off, so
`ObjectsEntityGet200ResponseInner(done = 1)` encodes exactly `{"done":1}`.
Regression guard: shopping-list case in
`data/src/jvmTest/.../datasource/remote/generic/GenericEntityDeserializationTest.kt`.

**Proposed upstream fix:** add `done` (and `qu_id`) to the `ShoppingListItem` schema.

## 6. Spec fails OpenAPI validation

Generation requires `--skip-validate-spec` (the dangling `$ref`s of item 4 alone break
validation).

**Proposed upstream fix:** items 4–5; then validation can be re-enabled here.
